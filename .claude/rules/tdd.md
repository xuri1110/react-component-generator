# TDD Rule

> **이 규칙은 Rigid다 — 상황에 맞게 완화하거나 변형하지 마라.**
> "이번만 예외"는 없다. 예외가 필요하다고 느껴지면 아래 [변명 차단표](#변명-차단표)부터 확인하라.

## 0. 프로젝트별 규칙 우선 조항

- 이 파일은 **기본값(fallback)** 이다.
- 프로젝트 루트의 `CLAUDE.md` 또는 `AGENTS.md`에 TDD 관련 규칙이 명시돼 있으면 **그쪽이 우선**한다.
- 프로젝트 문서에 규칙이 없거나 일부만 다룰 때만 이 파일의 나머지 항목으로 보충한다.

## 1. 적용 기준

### 반드시 TDD 적용

- **비즈니스 로직** (도메인 규칙, 계산, 상태 전이)
- **API/엔드포인트 핸들러** (요청 검증, 응답 형태, 에러 처리)
- **유틸리티/순수 함수** (입출력이 명확한 변환·파싱 로직)
- **버그 수정** — 수정 전에 그 버그를 재현하는 실패 테스트부터 작성한다

### TDD 불필요

- **타입 정의** (interface, type alias)
- **설정 파일** (config, env, 빌드 스크립트)
- **순수 UI/마크업** (스타일링만 있는 프레젠테이션 컴포넌트, 로직 없음)
- **SQL/마이그레이션 스크립트**

판단이 애매한 대상(예: 로직이 섞인 UI 컴포넌트)은 **로직 부분만 분리해 TDD 적용 대상으로 취급**한다.

## 2. RED-GREEN-REFACTOR 사이클

### RED

- **하나의 동작 = 하나의 테스트.** 여러 동작을 한 테스트에 욱여넣지 마라.
- 테스트를 작성한 뒤 **반드시 실행해서 실패를 눈으로 확인**한다. 실행하지 않고 넘어가는 것은 RED가 아니다.
- 실패 이유는 **"기능이 아직 구현되지 않았기 때문"** 이어야 한다. 문법 오류, import 누락, 오타로 인한 실패는 RED로 인정하지 않는다 — 고치고 다시 실행하라.

### GREEN

- 테스트를 통과시키는 **최소한의 코드만** 작성한다. **YAGNI** — 지금 테스트가 요구하지 않는 기능은 만들지 않는다.
- 구현 후 **신규 테스트와 기존 테스트 전부**를 실행해 통과를 확인한다. 일부만 돌려보고 넘어가지 마라.

### REFACTOR

- 중복 제거, 이름 개선, 헬퍼/모듈 추출을 수행한다.
- 전체 테스트가 **green을 유지**하는 상태에서만 진행한다. 하나라도 깨지면 즉시 되돌린다.
- 이 단계에서 **새로운 동작을 추가하지 않는다.** 새 동작이 떠올랐다면 다음 사이클의 RED로 넘긴다.

### 반복

- REFACTOR가 끝나면 다음 동작에 대한 **RED로 돌아간다.** 사이클을 건너뛰지 마라.

## 3. 삭제 강제 규칙

- 테스트보다 프로덕션 코드를 먼저 작성했다는 사실을 인지한 순간, **그 프로덕션 코드를 삭제**하고 RED부터 다시 시작한다.
- "어차피 짠 코드니까 참고용으로 남긴다"는 **금지**한다. 주석 처리, 별도 파일 보관, `_old` 접미사 등 어떤 형태로도 남기지 마라.

## 변명 차단표

| 변명 | 반론 |
|---|---|
| "너무 단순해서 테스트가 불필요하다" | 단순한 로직일수록 테스트 작성 비용도 낮다. 단순함은 생략의 근거가 아니라 오히려 즉시 작성 가능하다는 근거다. |
| "나중에 테스트를 추가하겠다" | "나중"은 오지 않는다. 테스트 없는 코드는 이미 배포/병합되는 순간 검증 부채로 고정된다. |
| "시간이 없다" | 테스트 없이 짠 코드가 원인 불명 버그를 만들면 디버깅에 더 많은 시간이 든다. TDD는 시간을 아끼는 방법이지 쓰는 방법이 아니다. |
| "삭제하면 낭비다" | 검증되지 않은 코드를 남기는 것이 더 큰 낭비다 — 나중에 그 코드를 신뢰할 수 없어 다시 검토해야 한다. |
| "이건 프로토타입이다" | 프로토타입이 프로덕션으로 승격되는 경우가 실제로 발생한다. 프로토타입으로 남길 것이면 별도 브랜치/디렉토리로 명확히 격리하고, 프로덕션 코드베이스에는 들이지 마라. |
