# commit: 변경사항 분석 후 자동 커밋

작업 디렉토리의 변경사항을 파악해 논리적 단위로 묶고, 저장소 컨벤션에 맞는 한국어 커밋 메시지를 작성해 **승인을 기다리지 않고 바로 커밋**한다. 이 스킬을 호출하는 것 자체가 사용자의 승인이므로, 매 실행마다 다시 확인받지 않는다. 단, Step 2의 시크릿 파일 예외는 그대로 지킨다.

## Step 0: 사전 확인

- `git rev-parse --is-inside-work-tree`로 git 저장소인지 확인한다. 아니면 사용자에게 알리고 종료한다.
- 저장소 루트의 `AGENTS.md`(없으면 `CLAUDE.md`)에 커밋 메시지 컨벤션(타입 목록, 언어, 스코프 표기, 이슈 번호 규칙 등)이 명시돼 있으면 이후 전 단계에서 그 규칙을 우선 적용한다. 명시된 규칙이 없으면 아래 "커밋 메시지 규칙"을 기본값으로 쓴다.

## Step 1: 변경사항 분석

다음을 병렬로 실행해 현재 상태를 파악한다:

- `git status` (미추적 파일 포함, `-uall`은 쓰지 않는다)
- `git diff` (unstaged) 및 `git diff --staged` (이미 staged된 것이 있으면)
- `git log --oneline -20` (기존 커밋 메시지 스타일·언어·타입 표기 관례 확인)

변경사항이 전혀 없으면(스테이지·언스테이지·미추적 파일 모두 없음) 그 사실을 알리고 종료한다.

## Step 2: 논리적 단위로 분류

전체 diff를 훑고, **하나의 커밋에는 하나의 목적만** 담기도록 변경 파일을 묶는다.

- 서로 관련 없는 변경(예: 기능 추가 + 포맷 정리 + 오타 수정)은 별도 커밋으로 분리한다.
- 같은 목적을 위해 여러 파일이 함께 바뀐 경우(예: 컴포넌트 + 그 스타일 + 그 테스트)는 한 커밋으로 묶는다.
- 분리 여부가 애매하면 더 잘게 쪼개는 쪽을 기본값으로 판단하고 바로 진행한다(사용자에게 묻지 않는다).
- 이 저장소에 특정 파일이 시크릿·자격증명으로 의심되면(예: `.env`, `*.pem`, 하드코딩된 토큰) **이 경우에만 예외적으로** 어떤 커밋에도 포함하지 말고, 그 파일을 제외한다는 사실과 이유를 알린 뒤 나머지는 계속 자동으로 진행한다(전체를 멈추지 않는다).

## Step 3: 커밋 메시지 작성

분류된 단위마다 한국어 커밋 메시지를 작성한다.

### 커밋 메시지 규칙 (저장소에 별도 컨벤션이 없을 때 기본값)

- 형식: `{type}: {한국어 요약}` — 제목은 50자 내외, 마침표 없이, 명령형/서술형으로 간결하게.
- type은 변경 내용에 맞게 다음 중 하나를 고른다:
  - `feat`: 새 기능 추가
  - `fix`: 버그 수정
  - `refactor`: 동작 변화 없는 구조 개선
  - `chore`: 빌드/설정/의존성 등 잡무성 변경
  - `docs`: 문서만 변경
  - `test`: 테스트 추가/수정
  - `style`: 포맷팅 등 비기능적 변경
  - `perf`: 성능 개선
- 본문(필요할 때만): 무엇을 바꿨는지가 아니라 **왜** 바꿨는지를 1~2문장으로. diff를 보면 알 수 있는 내용은 반복하지 않는다.
- 저장소의 `git log` 관례가 이 기본값과 다르면(예: 영어 사용, 다른 타입 접두어, 스코프 표기 `type(scope):`) 기존 관례를 따른다.

## Step 4: 커밋 계획 안내

커밋을 실행하기 직전(또는 직후) 무엇을 했는지 알 수 있도록 계획을 표 또는 목록으로 보여준다. 이 안내는 승인을 구하는 질문이 아니라 **진행 상황 보고**이며, 사용자 응답을 기다리지 않고 바로 Step 5로 넘어간다:

```
커밋 계획

1. [feat: 프롬프트 예시 칩 추가]
   - src/components/PromptInput.tsx
   - src/App.css

2. [fix: 다크 배경에서 안 보이던 결과 헤더 텍스트 수정]
   - src/App.css
```

## Step 5: 커밋 실행

분류된 단위마다:

1. 해당 단위에 속한 파일만 이름으로 지정해 `git add`한다 (`git add -A`/`git add .` 금지). staging 후 `git status`로 의도한 파일만 포함됐는지 확인한다.
2. 커밋 메시지는 HEREDOC으로 전달해 개행·따옴표가 깨지지 않게 한다.
3. 시스템 지침에 attribution 문구(예: `Co-Authored-By: ...`)가 지정돼 있으면 커밋 메시지 마지막에 그대로 포함한다.
4. 각 커밋 후 `git status`로 성공을 확인하고 다음 단위로 넘어간다.
5. pre-commit 훅 실패 시 `--no-verify`로 우회하지 말고, 원인을 고친 뒤 **새 커밋**으로 다시 시도한다(직전 실패 커밋은 만들어지지 않았으므로 `--amend` 대상이 아니다).

## 하지 않는 것

- 커밋은 승인 없이 자동으로 진행하지만, `git push`, `--amend`, `--force`, `--no-verify`, `--no-gpg-sign`은 이 스킬의 자동 승인 범위 밖이다. 사용자가 명시적으로 요청하지 않는 한 쓰지 않는다.
- 커밋 메시지에 diff 원문을 그대로 붙여넣거나, 반대로 "여러 파일 수정" 같은 의미 없는 요약을 쓰지 않는다.
- 시크릿으로 의심되는 파일이 있어 제외한 경우를 제외하면, 변경사항이 있는데 아무것도 커밋하지 않고 끝내지 않는다.
